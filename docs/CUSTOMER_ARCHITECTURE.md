# Customer application architecture

## Target configuration

[BusinessConfig](../LeafLaunch/Helpers/BusinessConfig.swift) reads target-specific constants emitted into Info.plist by [LeafLaunch.xcconfig](../Configurations/LeafLaunch.xcconfig). The existing LeafLaunch target is dedicated to store `ba6266df-513d-5b44-a58b-6e209284ceac`. Its public app key, `2fec1b48-f628-5ad6-8772-e15f432c8d14`, is the matching configuration UUID in `LeafLaunch-api/src/scripts/migrationData.ts`.

An app key identifies a `StoreAppConfiguration`; it is a public configuration identifier, not a Firebase token or secret. The API resolves branding, availability, age policy, minimum versions, and locations from it. Each additional business needs a separate Xcode target and xcconfig with its own IDs, logo asset, bundle identifier, signing, and Firebase iOS app registration/plist. All branded apps sharing LeafLaunch sign-in must register in the same Firebase Authentication project as the API token verifier; a different project's UID/email does not establish the same global Account. Include the shared Swift sources in that target. Do not choose tenants at runtime.

The target retains its provisioned `com.lltemplate` bundle identifier. Its Firebase plist and API StoreAppConfiguration fixture use project `leaflaunch-cfd63` and iOS app `1:198677595159:ios:34290bed90bb041cf94852`. The existing local API service-account project agrees with this registration; credentials remain outside source control. Device registration still requires the configured platform identifier and app key. Deployed Firebase credentials and APNs delivery must be verified in the deployment environment.

Target-specific `LEAFLAUNCH_DEVELOPMENT_API_URL` and `LEAFLAUNCH_PRODUCTION_API_URL` values flow through Info.plist and BusinessConfig. Debug and Development use the supplied `http://localhost:3000/api` backend; Localhost and custom environments remain deliberate development choices. Production requires an absolute HTTPS base URL, rejects loopback hosts, and has no localhost fallback. Its URL remains empty until a confirmed deployment value is supplied. Missing or malformed environment metadata defaults to Production, so it fails closed. The mock target makes no HTTP calls and needs neither URL.

## LeafLaunch Mock target

Select the shared **LeafLaunch Mock** scheme to run the same customer experience without a backend or Firebase account. Its [configuration](../Configurations/LeafLaunch%20Mock.xcconfig) uses bundle ID `com.lltemplate.mock` and defines `LEAFLAUNCH_MOCK` in every build configuration, including Release. The target shares the app sources, assets, and packages; it excludes the Firebase plist, push entitlement, and Crashlytics upload phase. AppDelegate skips Firebase initialization and remote-notification registration for this target.

AppAssembler installs mock API, authentication, Firebase, analytics, and connectivity services into `Container.shared` before resolving ViewModels. Navigation, alerts, persistence, launch, and lifecycle services retain their normal behavior. Backend methods return local values through the existing APIServiceProtocol; no HTTP API requests are needed. Product images use deterministic Picsum URLs and require internet access.

All fixture data is in [MockModels.swift](../LeafLaunch/DI/Mock/MockModels.swift), including preview fixtures. It mirrors the first LeafLaunch-Web owner workspace, **High Standards**, Store `80000000-0000-4000-8000-000000000001`. Names, addresses, category assignments, starting product prices and availability, marketing copy, schedules, and loyalty entries come from `LeafLaunch-Web/src/services/demo/` and `strings.ts`. Reserved demo support values (`+1 (949) 555-0100` and `hello@highstandards.example`) populate the Store Info contact rows. Random web record IDs are stable local IDs here, and relative schedules restart with the app. Only customer-visible locations, products, current promotions, and upcoming events are exposed; owner drafts and archived records stay outside the customer experience. The web workspace's unfinished launch readiness is treated as available so the complete customer flow can be exercised. Selected native mock products add three size/pack pricing options and typed attributes (text, selections, booleans, and measurements) to exercise product details. Their original first-variant IDs, starting prices, missing-price cases, and listing availability remain intact; category attribute IDs include those supplied by their products.

Every browsable mock Location has five clearly named active promotion examples, including **Capitol Hill Storefront** while its archive date is still in the future, alongside **Pearl District Shop** and **Old Town Shop**. **General Announcement** is display-only. **Sale: Featured Product** opens one published local product. **New Products: Explore The Collection** opens a list containing that product and a business product unavailable locally. **Visit Our Website** opens `https://example.com` externally. **Available At Another Location** exercises the single-product unavailability alert. Linked IDs come from the real mock catalog; unavailable examples have a published listing at another browsable Location and no public listing at the current one. These examples share titles, descriptions, and the website destination with the Web demo, retain relative schedules, and never invent promotion prices. Restart the mock app to reload the fixtures.

The app starts signed in as the owner's seeded customer **Alexis Mensah** (`alexis.mensah@example.com`), membership **LEAF2345**, with **1,235 points** and all 30 ledger entries. The Pearl District Shop and Capitol Hill Storefront share that business-wide balance and history. Old Town Shop starts without a location membership and supports joining. The real location picker and age-21 gate remain active. Sign out to exercise guest browsing, local login, signup, and password reset. Mock login accepts the form's valid inputs and reuses the current simulated business customer profile. Signup starts a fresh synthetic authentication session, creates a customer profile/code with zero points and no Location memberships, and reuses that profile/code on subsequent same-session registration without overwriting its name or balance. Registration requires the matching Store ID and no selected Location. Location enrollment remains separate. An anonymized mock profile cannot be reused by the same session. These local identities do not verify Firebase credentials or shared sign-in across real branded apps. Profile edits, joining, and account deletion mutate the in-memory mock session. Relaunching restores Alexis and the original fixtures. Favorites, selected location, guest approvals, and theme preferences persist in the mock app’s separate defaults. Authenticated mock age acceptances are session-owned and reset on relaunch, so the customer affirms again even when local approval metadata remains.

## Launch and navigation

`LeafLaunchApp.init` resolves UserDefaultsService and synchronously restores cached branding before resolving RootViewModel. RootScreen's `.task` starts `RootStartupService`, which waits for optional existing authentication, StoreSession bootstrap, and the splash callback. Guest access never depends on account creation. Bootstrap failures finish the splash gate and expose retry controls.

`StoreSessionService` owns the public configuration, explicit customer-safe `PublicStore`, and committed validated location. Bootstrap resolves the tenant from the public app key and checks the target Store ID. Hours requests carry the same app key and Store ID. The client verifies both returned identities and current availability before selection. A validated saved location restores automatically; without a saved choice, a sole location is selected automatically. Without a committed active location, the location sheet requires selection and cannot be dismissed. Missing age approval always requires a location tap first, including for an automatically selected sole location. An invalid cached choice is cleared when there is no active committed location. Store Info displays the actual location address and hours alongside available public support phone and email links.

The selected location’s server-resolved `EffectiveAgePolicy` controls access to that location's content. Only an explicit location selection can replace the picker with the non-dismissible native age sheet through NavigationService. A pending candidate supplies age context while the active location remains unchanged. The approval dictionary retains `[userId: [state]]`, using canonical country/region keys and a conservative missing-scope key. Separate metadata records scope, accepted minimum age, policy version, and approval revision. Unchanged or weaker requirements retain approval; a higher minimum age, changed scope, or explicit approval-revision change requires renewed affirmation. Legacy state-only entries have no policy evidence and deliberately require re-attestation. A stable persisted guest identity owns guest approval; authentication never transfers it to a customer.

Authenticated approval uses the existing AgeGateAcceptance GET/PUT contract with location context. The age-specific confirmation action commits local approval immediately and lets the sheet dismiss; StoreSessionService owns the background PUT independently of the sheet's lifetime. The server re-resolves policy and validates the displayed age/version. Background failures are logged, and subsequent entry still checks authenticated acceptance through GET. A policy-conflict response refreshes bootstrap and the selected policy before another explicit location selection and affirmation. Guests keep their local flow without registration. Identity, location, refreshed bootstrap, and foreground configuration changes reevaluate the gate and return to the picker when affirmation is needed. Superseded acceptance/selection work cannot approve another identity or location. Device registration likewise owns a cancellable request and verifies the current customer/Firebase UID; cached Firebase tokens are UID-scoped and stale refresh results cannot survive account changes.

Main keeps StoreDetails and its TabBarNavigationService at the root, with one NavigationStack per tab and no enclosing stack. A stable Main-level NavigationService sheet hosts location selection and age verification. Change Location opens the picker while preserving the active store, tab paths, and persisted choice. When opened from an approved active store, Close or native swipe dismissal cancels the pending selection and returns the session to that same store without persisting anything. StoreSessionService owns this eligibility only while the opening identity matches the committed store identity; bootstrap, identity changes, and required age re-attestation clear it. Main forwards the native sheet dismissal into the same guarded cancellation method, while initial selection and age verification stay non-dismissible. Successful selection commits and persists the candidate before dismissing the sheet. A different location resets tab paths, presentations, and selected tab and creates fresh feature ViewModels with location context before lifecycle work; reselecting the current location preserves its tab flow. Cancelled or failed selection cannot replace the active store. Route-created product screens receive their location/product context before lifecycle work.

`StoreDetails/` has four feature/shared folders:

- `Overview/`: promotions, a ten-event preview with a pushed paginated Events screen, featured products, and Store Info with actual location, hours, and support contacts.
- `Shop/`: the Menu tab with category/subcategory filtering, search, server sorting, Rune pull-to-refresh, paginated products, nested product details, and pushed FavoriteProductsScreen/FavoriteProductsViewModel. Store, Menu, and Account are the three customer tabs.
- `Account/`: guest registration/login actions, customer profile, loyalty balance, and a recent activity preview. `Account/PointsActivity/` owns the pushed, location-scoped ledger screen with the shared transaction rows, explicit pagination, retry, and authenticated identity cleanup. Your Store reuses the existing session-owned location sheet.
- `Shared/`: shared image-led product cards, price/media/favorite treatments, and an adaptive product grid.

Each screen owns one StateObject ViewModel. Child screens have dedicated paired files. Fetch-backed screens use `.task { [weak viewModel] in viewModel?.loadData(showHud: true) }` for initial/reappearance loading. First appearance installs navigation, tracks, and binds subscribers without duplicating the fetch. ViewModels present errors through focused AlertService helpers and dismiss each task's unique loading alert in `defer`; views do not use `.errorHandler`. Shared domain models are split in `Models/Customer/`; feature-specific models live in lower-case `models/` folders.

## Customer identity and registration

The verified Firebase UID resolves one global LeafLaunch Account. Each business app resolves a separate CustomerAccount by that Account and its target Store ID. `AuthService` explicitly calls the idempotent registration command after email signup, email login, Apple authentication, and restored authentication before publishing the current business customer. It uses `BusinessConfig.businessId` and `x-app-key`; no selected Location is needed. Existing ACTIVE profiles retain their names, membership codes and balances. A Firebase duplicate-email signup presents LeafLaunch sign-in guidance and opens the existing login route; it never registers by email alone. A failed command remains an error rather than a reason to create from a GET or bypass customer status.

`CustomerAccount` includes global `account_id`, `store_id/store_name`, `membership_code`, and string `cached_points_balance`. The API creates the business profile and canonical loyalty account/code in one transaction. The live client verifies the returned Store ID. Account membership presentation reads these profile fields before any Location enrollment; local membership continues to own favorites, notifications and activity attribution. Customer anonymization affects only this business profile and retains the global identity and other business/Portal profiles.

## Endpoint mapping

| Mobile operation | Existing API |
| --- | --- |
| Bootstrap | `GET /v1/public/apps/{appKey}/bootstrap?platform=IOS&version=...&store_id=...` |
| Validate location, hours, and effective age policy | `GET /v1/public/locations/{locationId}/hours?store_id=...` with `x-app-key` |
| Categories | `GET /v1/public/locations/{locationId}/categories` |
| Product feed/details | `GET /v1/public/locations/{locationId}/products` and `.../products/{productId}` |
| Promotions/events | `GET /v1/public/locations/{locationId}/promotions` and `.../events` |
| Authenticated age affirmation | `GET/PUT /v1/customer/age-gate` with `location_id` (query/body) and `x-app-key` |
| Customer profile | `GET/PATCH/DELETE /v1/customer/account` |
| Register/ensure business profile | `POST /v1/customer/account` with `{ store_id, display_name }` and `x-app-key`; no selected Location |
| Membership | `GET/POST /v1/customer/locations/{locationId}/membership` |
| Points history | `GET /v1/customer/locations/{locationId}/loyalty` |

Public calls explicitly bypass bearer authentication while carrying public tenant context. Customer calls obtain a fresh Firebase bearer token and pass `x-app-key` plus location context where required. Page responses retain server metadata; money uses Decimal, points preserve API strings, and product attribute values support the API’s primitive/array union.

The overview requests events with `limit=10`. The Events screen uses the same endpoint with explicit offsets and twenty-item pages; reappearance refreshes the previously loaded range in requests capped at one hundred items. Featured Products uses the existing product feed with `sort=featured` and `limit=6`.

`ProductQuery.sort` sends `featured`, `name`, `price_ascending`, or `price_descending`. The API orders the full filtered result before pagination. StoreShop never downloads the whole catalog to sort it; filter, search, and sort changes cancel old requests and reset paging, and load-more retains the selected order. Price ordering and the row’s “from” amount use the minimum display price among available variants of a published listing. Individual variant details retain visible prices and availability labels; products without an available price sort last. See the API’s [catalog rules](../../LeafLaunch-API/docs/UBIQUITOUS_BUSINESS_LOGIC.md#shared-product-versus-local-listing) for missing-price and tie-breaking semantics.

The storefront composition in [DESIGN.md](../DESIGN.md) uses shared Rune-backed commerce surfaces and focused feature views. The catalog initially selects the first real category and its first subcategory. Its stacked parent/child rails and native Filters menu share the existing server query IDs; changing the parent selects its first child. No synthetic All option is exposed. Refresh preserves valid selections and falls back to the first real category/child when a selection disappears. The two rails animate their selected underlines through separate persistent matched-geometry namespaces. Every new surface consumes the active environment style, so store-defined colors, fonts, and radii continue to control its appearance without a second theme system.

Public product feed/details responses include active media with a directly loadable `url`; categories use nullable `image_url`, bootstrap branding uses optional `logo_url`, `icon_url`, and `splash_url`, and promotion/event images contain `url`. Customer models do not carry object keys or MIME types. Menu, Favorite Products, and product details pass response URLs straight to Rune ImageSource without additional backend URL requests or client-side MIME filtering. Rune owns image loading, caching, and failed-image placeholders. Product details retain the ordered gallery with stable selected-media identity, paging, and thumbnails. Catalog refreshes replace product media and URLs together. Product variants expose their display price and availability; promotion kinds do not alter pricing or supply discount/base-price fields.

Public promotions use `GENERAL`, `SALE`, `NEW_PRODUCT`, and `LINK`. Every response supplies nullable `url`, business-level `linked_product_ids`, and `linked_products` summaries with a StoreProduct `id`, `display_name`, and nullable `location_product_listing_id`. Linked business products remain in the response even when not assigned or visible at the selected location. GENERAL banners have no tap action or tap analytics. SALE and NEW_PRODUCT open the existing product details directly for one linked product, or push PromotionProductsScreen for several. The list retains unavailable products and selecting one presents the existing AlertService with location availability guidance. Available summaries use their location listing ID for the existing product route. LINK validates an HTTPS URL defensively and opens it externally through UIApplication; an invalid URL or failed open presents AlertService feedback. Existing push/deeplink services retain their current limited route handling; this flow adds banner actions only. Offline fixtures cover all four kinds, single/multiple products, and unavailable links.

## Persistence and theme

Customer keys are scoped by business, app key, and bundle. They include the cached theme definition, `last_selected_location_id`, identity-keyed approved states, guest identity, and favorited product IDs. Logout preserves browsing preferences and removes existing sensitive security-pin state.

Rune Theme contains UI types and is not Codable. `CachedStoreTheme` persists the canonical validated branding definition, resolved radius roles, fallback preference, and target/schema metadata; StoreThemeBuilder reconstructs the actual Rune Theme synchronously. Theme preference changes preserve the fetched definition. Cache schema 2 records all seven supported Rune radius roles in logical points, bounded to 0–100. Missing values resolve from LeafLaunchThemeTokens: `extra_small=2`, `small=4`, `small2=6`, `medium=10`, `medium2=14`, `large=20`, and `extra_large=28`; Rune’s `none` remains zero.

App Style now carries eight independent optional base colors: background, content background, title, body, accent, button, button title and icon. These map to Rune's existing background.primary/secondary, textColor.title/body, palette.link/highlight, foreground.primary (CommonButton fill), and foreground.secondary respectively. Button Title Color maps directly to textColor.button (text(.button)); only an omitted button title color uses derived contrasting text. Button fill, button title and accent tint remain independent. Configured base values remain exact; StoreThemeColors and StoreThemeColor derive only supporting shades in OKLCH, including nested surfaces, icon variants, inverted/placeholder/button text and skeleton. The deterministic derivation, gamut mapping and contrast rules are documented in the [API runtime theme contract](../../LeafLaunch-API/docs/UBIQUITOUS_BUSINESS_LOGIC.md#runtime-theme-definition). Derived colors are reconstructed, never cached individually. Web intentionally previews the selected colors only and performs no color derivation. Native derives readable supporting colors where possible, but arbitrary low-contrast configured bases are not silently changed.

Font Family is typed by StoreAppFontFamily: System, Avenir Next, Helvetica Neue, Arial, Georgia, Palatino, Menlo or Courier New. StoreThemeFonts applies the selected family while retaining role sizes and weights; System uses the built-in system fonts, and unavailable families use those same defaults. The Web preview uses local fonts with an explicit generic fallback and never downloads font assets.

Schema 1 color/font/media definitions migrate synchronously with those established radius defaults. Corrupt, invalid, incomplete schema-2, unknown-schema, or foreign-target caches are removed and fall back to the built-in theme. First launch also uses that default. No arbitrary expiration or asynchronous startup theme application is added. Spacing, shadows, and interaction tokens remain owned by the existing app defaults because the API does not configure those roles.

## Public launch contract and domain authority

The API calls the tenant a Store. `store_id` and the customer-safe `store` projection identify that tenant; the app key identifies its StoreAppConfiguration and grants no authentication authority. Bootstrap retains existing launch state, update URL, feature flags, Store-wide gate fields, canonical branding, and available-location summaries, with each location’s effective age policy. The public hours response uses an explicit location projection including address, hours, and schedule exceptions; protected Store/staff/customer/billing relationships and Firebase credentials never enter these public payloads.

Regional configuration, restriction precedence, version allocation, administrative permissions, and accepted policy evidence are owned by the API’s [business rules](../../LeafLaunch-API/docs/UBIQUITOUS_BUSINESS_LOGIC.md#legal-bootstrap-and-hours) and [language](../../LeafLaunch-API/docs/UBIQUITOUS_LANGUAGE.md#store-location-app-legal-and-billing). The supplied business policy requires 18+ approval across all US states. The target fixture expresses it as one US country rule (`country_code=US`, `region=null`, required, minimum age 18); regional configuration currently accepts US scope only and compares region identifiers with the Location’s canonical stored values. Existing stricter Store restrictions remain effective. A confirmed production HTTPS API URL remains an external deployment value.

The customer app reads loyalty balance and redemption/spending history through membership and ledger; it has no checkout, payment, or points-spending flow. Verification follows [AGENTS.md](../AGENTS.md#verify-and-maintain). Source checks do not establish iOS SDK compatibility, push delivery, or device behavior.
