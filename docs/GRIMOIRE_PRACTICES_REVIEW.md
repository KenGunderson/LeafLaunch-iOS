## Cumulative rules and superseded details

- Loading and alert rules are one responsibility: cancel/own work, snapshot context, commit on the main actor after checks, dismiss the exact loader, keep failure distinct from empty success, retain refresh values, and leave retry reachable. A focused success/error helper and centralized copy do not justify a presentation framework.
- The final composition rule requires small named `@ViewBuilder` methods, including one-container helpers. It supersedes earlier advice to annotate only helpers with conditional or multiple roots. `content()` composes sections/actions; collections compose row/card helpers. This is local extraction, not extra model/service layers.
- Repeated Rune defaults belong in app-owned components or modifiers with a small current-use API. Migrate matching callers while preserving keyboard/focus/validation, context, lifecycle, and navigation. A generic upstream wrapper is not required when an existing commerce component already owns the same responsibility.
- Grimoire's intermediate `.small2`/shadow-free cards and 1.5-point border were replaced there by `.medium2` padding, `.large` radius, subtle shadow/inset stroke, and 0.75-point border. Those are final Grimoire visuals, not mandatory LeafLaunch values. LeafLaunch's documented store branding and established component defaults govern its visuals.
- Nav/tab accessibility overrides added in `753f09f` were removed in `ba3d0f7`. They are not a cumulative upstream mandate or a reason to remove LeafLaunch's existing accessible behavior. Modal accessibility and reachable dismissal from the final example remain applicable.
- The later Grimoire registry, user-defaults default, mock assembler, mock setter, typography, theme samples, and design contract form a coherent example of one theme authority. LeafLaunch retains its Light/Dark registry, target-scoped cached StoreAppBranding, supported radius roles, synchronous restoration, and live/mock behavior. It does not gain Grimoire/Parchment themes, assets, or serif fonts.

## LeafLaunch-specific boundaries

- Root/startup and splash preserve their existing lifecycle, coordinator, and feedback ownership. Fetch-backed customer screens retain `.task` loading and first-appearance tracking/binding; no empty hooks are added to screens without fetching/subscriptions.
- Account authenticated-user/request IDs, catalog query generations, pagination/mutation single-flight behavior, service isolation, and request/session guards remain authoritative. The replacement example is not a reason to erase stronger ownership or repeat side-effecting requests.
- StoreDetails owns four customer navigation roots. Tab clearance belongs inside tab-root scrolling content. The account auth-route safe-area inset remains an intentional exception for pushed authentication screens. Contextual CommerceEmptyState keeps filters/actions accessible and does not become a root overlay. Home's intentional default `.large` horizontal padding is not normalized to `.medium`.
- The Grimoire tab showcases, local project demonstrations, workspace/store-info screenshot, theme palette, font families, reduced radius numbers, card ornament, and animation curve do not define LeafLaunch product requirements. Existing [DESIGN.md](../DESIGN.md) and the [customer architecture](CUSTOMER_ARCHITECTURE.md) retain visual and domain authority.
- LeafLaunch's `AuthServiceProtocol.reloadUser()`, `LLUser`, `NavHeader`, commerce components, customer routes, live/mock API contracts, and explicit Xcode project membership remain the actual integration contracts. New independent models stay in separate files near their owner.
